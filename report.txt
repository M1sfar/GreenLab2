Выбранные проверки независимости условий:
Для доказательства независимого срабатывания каждой блокировки полива (R06, R07, R08) выбраны 4 минимальных опыта (комбинации 1–4): базовый разрешённый случай без блокировок (комбинация 1) и три случая, в каждом из которых активна ровно одна блокировка при снятых двух остальных (комбинации 2, 3, 4). Этого достаточно, чтобы однозначно убедиться, что каждое условие блокирует насос самостоятельно без фиксации fault. Комбинации 5–8 (одновременное действие двух или трёх запретов) оставлены непроверенными сознательно: по спецификации все три запрета объединяются логическим «ИЛИ» (cold || rain || lowTank) и приводят к идентичному выходу (pump=false, fault=false, used=0), поэтому их перебор не добавляет новой диагностической информации при проверке независимости.

NORMAL→FAULT:
NORMAL --[некорректный вход (R01) ИЛИ age > 30 (R02)]--> FAULT (pump=false, vent=false, fault=true, used=0). Валидный свежий вход (age <= 30) оставляет систему в NORMAL; запреты temp<=3, rain=true, tank<10 и нехватка бюджета НЕ переводят систему в FAULT.

FAULT→FAULT:
FAULT --[некорректный вход (R01) ИЛИ age > 30 (R02)]--> FAULT (даже при reset=true авария не снимается); FAULT --[валидный свежий вход (age <= 30) И reset = false]--> FAULT (удержание аварии R03, устройства выключены, used=0).

FAULT→NORMAL:
FAULT --[валидный свежий вход (age <= 30) И reset = true]--> NORMAL (авария снимается и на этом же шаге выполняется штатное управление; reset без аварии не обнуляет память гистерезиса).

Память pump/vent, два одинаковых конечных входа после разных историй:
Фактическое состояние насоса (previous.pump): false -> true при humidity < 35, отсутствии запретов (temp > 3, rain = false, tank >= 10) и остатке бюджета >= 2; true -> true (удержание) при 35 <= humidity < 45, отсутствии запретов и бюджете >= 2; true -> false при humidity >= 45 ИЛИ срабатывании запрета ИЛИ нехватке бюджета (при отключении из-за запрета или бюджета фактическая память становится false).
Фактическое состояние вентиляции (previous.vent): false -> true при temp >= 30 и бюджете >= 3; true -> true (удержание) при 26 < temp < 30 и бюджете >= 3; true -> false при temp <= 26 ИЛИ бюджете < 3.
Общий финальный вход (Шаг 2): { humidity: 40, temp: 28, age: 0, tank: 50, budget: 5, rain: false, reset: false }. Стартовое состояние обеих историй: pump = false, vent = false, fault = false.

Расчёт: вход валидный, свежий; humidity=20 < 35 -> запрос pump=true; temp=31 >= 30 -> запрос vent=true; запретов нет; budget=5 хватает на vent (3) + pump (2). Итог Шага 1 (память для Шага 2): pump = true, vent = true, fault = false, used = 5.
  * Шаг 2: вход { humidity: 40, temp: 28, age: 0, tank: 50, budget: 5, rain: false, reset: false }. ## 4. Дефект (повторить на каждый)
ID, R-ID, заголовок: BUG-01, R05, Включение насоса на точной границе влажности humidity = 35 (нестрогое сравнение вместо строгого)
Начальное состояние и минимальные шаги: Начальное состояние: pump = false, vent = false, fault = false. 1. Вход: { "humidity": 35, "temp": 20, "age": 0, "tank": 50, "budget": 5, "rain": false, "reset": false }
Ожидание с ручным обоснованием: По требованию R05 запрос на включение полива формируется только при строгом неравенстве humidity < 35, а интервал 35 <= humidity < 45 является зоной гистерезиса (сохраняется previous.pump = false). Запретов нет, бюджет 5 достаточен. Ожидаемый результат: pump = false, vent = false, fault = false, used = 0.
Факт и ссылка на локальный протокол: Фактический результат: pump = true, vent = false, fault = false, used = 2 (FAIL). Ссылка: protocol-before.txt, сценарий «T05: R05 границы гистерезиса полива 35 и 45», шаг 2.
Серьёзность и риск: Средняя (Major). Нарушение нижней границы гистерезиса приводит к преждевременному запуску полива на пороге 35% и сужению зоны нечувствительности контроллера, увеличивая риск избыточного полива и дребезга реле при колебаниях влажности вокруг 35%.
Причина в candidate.js: В функции pumpStart вместо строгого оператора < использован нестрогий оператор <=: pumpStart: humidity => humidity <= 35.
Исправление до/после: До: pumpStart: humidity => humidity <= 35, | После: pumpStart: humidity => humidity < 35,
Регрессия: Повторный прогон сценария «T05: R05 границы гистерезиса полива 35 и 45» (шаги 1–5: проверка точек 35.1, 35, 34.9, 44.9, 45) и сценария T08 подтверждает корректное удержание OFF на humidity = 35 и старт только при humidity = 34.9.

ID, R-ID, заголовок: BUG-02, R03, Самопроизвольный сброс аварийного состояния fault на свежем валидном снимке без команды reset = true
Начальное состояние и минимальные шаги: Начальное состояние: pump = false, vent = false, fault = false. 1. Вход: { "humidity": 20, "temp": 20, "age": 31, "tank": 50, "budget": 5, "rain": false, "reset": false } (перевод в fault по R02). 2. Вход: { "humidity": 20, "temp": 20, "age": 0, "tank": 50, "budget": 5, "rain": false, "reset": false } (валидный свежий снимок без сброса).
Ожидание с ручным обоснованием: По требованию R03 зафиксированная авария (previous.fault = true) должна удерживаться на последующих шагах до явного получения команды reset = true на валидном свежем входе; свежие валидные данные сами по себе не снимают аварию. На шаге 2 reset = false, следовательно, система должна оставаться в состоянии аварии: pump = false, vent = false, fault = true, used = 0.
Факт и ссылка на локальный протокол: Фактический результат на шаге 2: pump = true, vent = false, fault = false, used = 2 (FAIL). Ссылка: protocol-before.txt, сценарий «T06: R03 удержание аварии fault и восстановление по reset», шаг 2.
Серьёзность и риск: Высокая (Critical). Самопроизвольный выход из аварийного режима и включение исполнительных механизмов без подтверждения оператором (reset = true) после сбоя датчиков нарушает требования безопасности и может привести к аварийной работе оборудования (приоритетный риск №2 из Раздела 1).
Причина в candidate.js: В функции удержания аварии hold добавлено ошибочное условие && input.age > 30: hold: (previous, input) => previous.fault && !input.reset && input.age > 30.
