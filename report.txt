## 3. Таблицы и состояния
### Графы переходов состояний
1. Переходы аварийного состояния (NORMAL <-> FAULT):
   - NORMAL --[некорректный вход (R01) ИЛИ age > 30 (R02)]--> FAULT (pump=false, vent=false, fault=true, used=0)
   - FAULT  --[некорректный вход (R01) ИЛИ age > 30 (R02)]--> FAULT (даже при reset=true авария не снимается)
   - FAULT  --[валидный свежий вход (age <= 30) И reset = false]--> FAULT (удержание аварии R03, устройства выключены, used=0)
   - FAULT  --[валидный свежий вход (age <= 30) И reset = true]--> NORMAL (авария снимается и на этом же шаге выполняется штатное управление)
   - NORMAL --[валидный свежий вход (age <= 30), любой reset]--> NORMAL (штатная работа; запреты temp<=3, rain=true, tank<10 и нехватка бюджета НЕ переводят систему в FAULT)

2. Память исполнительных устройств (в состоянии NORMAL):
   - Фактическое состояние насоса (previous.pump):
     * false -> true: humidity < 35 И нет запретов (temp > 3, rain = false, tank >= 10) И хватает остатка бюджета (>= 2).
     * true -> true (удержание): (humidity < 35 ИЛИ 35 <= humidity < 45) И нет запретов И хватает остатка бюджета (>= 2).
     * true -> false: humidity >= 45 ИЛИ сработал любой запрет (temp <= 3, rain = true, tank < 10) ИЛИ не хватило бюджета (< 2). При отключении из-за запрета или бюджета фактическая память становится false.
   - Фактическое состояние вентиляции (previous.vent):
     * false -> true: temp >= 30 И хватает бюджета (budget >= 3).
     * true -> true (удержание): (temp >= 30 ИЛИ 26 < temp < 30) И хватает бюджета (budget >= 3).
     * true -> false: temp <= 26 ИЛИ не хватило бюджета (budget < 3).

### Память pump/vent: два одинаковых конечных входа после разных историй
Общий финальный вход (Шаг 2): { humidity: 40, temp: 28, age: 0, tank: 50, budget: 5, rain: false, reset: false }
Стартовое состояние обеих историй: pump = false, vent = false, fault = false.

- История А (предварительный запуск обоих устройств):
  * Шаг 1: вход { humidity: 20, temp: 32, age: 0, tank: 50, budget: 5, rain: false, reset: false }.
    Расчёт: вход валидный, свежий; humidity=20 < 35 -> запрос pump=true; temp=32 >= 30 -> запрос vent=true; запретов нет; budget=5 хватает на vent (3) + pump (2).
    Итог Шага 1 (память для Шага 2): pump = true, vent = true, fault = false, used = 5.
  * Шаг 2: вход { humidity: 40, temp: 28, age: 0, tank: 50, budget: 5, rain: false, reset: false }.
    Расчёт: humidity=40 попадает в зону гистерезиса [35; 45) -> сохраняется previous.pump = true; temp=28 попадает в зону гистерезиса (26; 30) -> сохраняется previous.vent = true; запретов нет; budget=5 покрывает оба устройства (3 + 2 = 5).
    Итог Шага 2: pump = true, vent = true, fault = false, used = 5.

- История Б (предварительный простой обоих устройств):
  * Шаг 1: вход { humidity: 50, temp: 20, age: 0, tank: 50, budget: 5, rain: false, reset: false }.
    Расчёт: вход валидный, свежий; humidity=50 >= 45 -> запрос pump=false; temp=20 <= 26 -> запрос vent=false; устройства не запрашиваются.
    Итог Шага 1 (память для Шага 2): pump = false, vent = false, fault = false, used = 0.
  * Шаг 2: вход { humidity: 40, temp: 28, age: 0, tank: 50, budget: 5, rain: false, reset: false }.
    Расчёт: humidity=40 попадает в зону гистерезиса [35; 45) -> сохраняется previous.pump = false; temp=28 попадает в зону гистерезиса (26; 30) -> сохраняется previous.vent = false; запросы отсутствуют.
    Итог Шага 2: pump = false, vent = false, fault = false, used = 0.

Вывод: при идентичном входном снимке на Шаге 2 выходные значения полностью противоположны (used=5 против used=0), так как оба параметра попали в зону нечувствительности (гистерезиса), где решение определяется фактическим состоянием предыдущего шага.

### Обоснование выбранных проверок независимости условий
Для доказательства независимого срабатывания каждой блокировки полива (R06, R07, R08) выбраны **4 минимальных опыта (комбинации 1–4)**: базовый разрешённый случай без блокировок (комбинация 1) и три случая, в каждом из которых активна ровно одна блокировка при снятых двух остальных (комбинации 2, 3, 4). Этого достаточно, чтобы однозначно убедиться, что каждое условие блокирует насос самостоятельно без фиксации `fault`. Комбинации 5–8 (одновременное действие двух или трёх запретов) оставлены непроверенными сознательно: по спецификации все три запрета объединяются логическим «ИЛИ» (`cold || rain || lowTank`) и приводят к идентичному выходу (`pump=false, fault=false, used=0`), поэтому их перебор не добавляет новой диагностической информации при проверке независимости.

## 4. Дефект (повторить на каждый)

### Дефект 1
ID, R-ID, заголовок: BUG-01, R05, Включение насоса на точной границе влажности humidity = 35 (нестрогое сравнение вместо строгого)

Начальное состояние и минимальные шаги:

Начальное состояние: pump = false, vent = false, fault = false.

1. Вход: { "humidity": 35, "temp": 20, "age": 0, "tank": 50, "budget": 5, "rain": false, "reset": false }

Ожидание с ручным обоснованием:

По требованию R05 запрос на включение полива формируется только при строгом неравенстве humidity < 35, а интервал 35 <= humidity < 45 является зоной гистерезиса (сохраняется previous.pump = false). Запретов нет, бюджет 5 достаточен. Ожидаемый результат: pump = false, vent = false, fault = false, used = 0.

Факт и ссылка на локальный протокол:

Фактический результат: pump = true, vent = false, fault = false, used = 2 (FAIL).

Ссылка: protocol-before.txt, сценарий «T05: R05 границы гистерезиса полива 35 и 45», шаг 2.

Серьёзность и риск:

Средняя (Major). Нарушение нижней границы гистерезиса приводит к преждевременному запуску полива на пороге 35% и сужению зоны нечувствительности контроллера, увеличивая риск избыточного полива и дребезга реле при колебаниях влажности вокруг 35%.

Причина в candidate.js:

В функции pumpStart вместо строгого оператора `<` использован нестрогий оператор `<=`: `pumpStart: humidity => humidity <= 35`.

Исправление до/после:

До: `pumpStart: humidity => humidity <= 35,`

После: `pumpStart: humidity => humidity < 35,`

Регрессия:

Повторный прогон сценария «T05: R05 границы гистерезиса полива 35 и 45» (шаги 1–5: проверка точек 35.1, 35, 34.9, 44.9, 45) и сценария T08 подтверждает корректное удержание OFF на humidity = 35 и старт только при humidity = 34.9.

### Дефект 2
ID, R-ID, заголовок: BUG-02, R03, Самопроизвольный сброс аварийного состояния fault на свежем валидном снимке без команды reset = true

Начальное состояние и минимальные шаги:

Начальное состояние: pump = false, vent = false, fault = false.

1. Вход: { "humidity": 20, "temp": 20, "age": 31, "tank": 50, "budget": 5, "rain": false, "reset": false } (перевод системы в аварию по устаревшему снимку R02 -> состояние становится pump = false, vent = false, fault = true).

2. Вход: { "humidity": 20, "temp": 20, "age": 0, "tank": 50, "budget": 5, "rain": false, "reset": false } (подача валидного свежего снимка без команды сброса).

Ожидание с ручным обоснованием:

По требованию R03 зафиксированная авария (previous.fault = true) должна удерживаться на последующих шагах до явного получения команды reset = true на валидном свежем входе; свежие валидные данные сами по себе не снимают аварию. На шаге 2 reset = false, следовательно, система должна оставаться в состоянии аварии: pump = false, vent = false, fault = true, used = 0.

Факт и ссылка на локальный протокол:

Фактический результат на шаге 2: pump = true, vent = false, fault = false, used = 2 (FAIL).

Ссылка: protocol-before.txt, сценарий «T06: R03 удержание аварии fault и восстановление по reset», шаг 2.

Серьёзность и риск:

Высокая (Critical). Самопроизвольный выход из аварийного режима и включение исполнительных механизмов без подтверждения оператором (reset = true) после сбоя датчиков нарушает требования безопасности и может привести к аварийной работе оборудования (приоритетный риск №2 из Раздела 1).

Причина в candidate.js:

В функции удержания аварии `hold` добавлено ошибочное условие `&& input.age > 30`: `hold: (previous, input) => previous.fault && !input.reset && input.age > 30`. Из-за этого на любом свежем снимке (`age <= 30`) условие `hold` возвращало `false` даже при `previous.fault === true` и `input.reset === false`.

Исправление до/после:

До: `hold: (previous, input) => previous.fault && !input.reset && input.age > 30,`

После: `hold: (previous, input) => previous.fault && !input.reset,`

Регрессия:

Повторный прогон сценария «T06: R03 удержание аварии fault и восстановление по reset» (шаги 1–4) и сценария T01 (шаг 2 -> шаг 3) подтверждает удержание fault = true при reset = false и штатный сброс только при reset = true.

### Дефект 3
ID, R-ID, заголовок: BUG-03, R09, Неверный приоритет распределения ограниченного бюджета (включение насоса вместо вентиляции при budget = 3 и двух запросах)

Начальное состояние и минимальные шаги:

Начальное состояние: pump = false, vent = false, fault = false.

1. Вход: { "humidity": 20, "temp": 31, "age": 0, "tank": 50, "budget": 3, "rain": false, "reset": false }

Ожидание с ручным обоснованием:

Вход валидный и свежий. При humidity = 20 < 35 запрашивается насос (стоимость 2), при temp = 31 >= 30 запрашивается вентиляция (стоимость 3). Запретов полива нет. По требованию R09 первой рассматривается вентиляция: бюджета 3 хватает на вентиляцию (остаток 3 - 3 = 0), после чего на насос ресурса не остаётся. Ожидаемый результат: pump = false, vent = true, fault = false, used = 3.

Факт и ссылка на локальный протокол:

Фактический результат: pump = true, vent = false, fault = false, used = 2 (FAIL).

Ссылка: protocol-before.txt, сценарий «T10: R09 конкуренция за бюджет (budget 1, 2, 3, 5)», шаг 3.

Серьёзность и риск:

Высокая (Critical). При дефиците энергии/ресурса контроллер отдаёт приоритет поливу вместо критически важного охлаждения теплицы при высокой температуре (temp >= 30), что напрямую реализует риск №1 (перегрев и гибель культуры).

Причина в candidate.js:

В методе `order` задан обратный порядок обхода устройств: `order: () => ['pump', 'vent']` вместо `['vent', 'pump']`. Из-за этого при budget = 3 первым выделяется ресурс 2 ед. на насос, а на вентиляцию остаётся 1 ед. (недостаточно).

Исправление до/после:

До: `order: () => ['pump', 'vent']`

После: `order: () => ['vent', 'pump']`

Регрессия:

Повторный прогон сценария «T10: R09 конкуренция за бюджет (budget 1, 2, 3, 5)» (шаги 1–4) и сценария T12 (шаг 2) подтверждает приоритет вентиляции при budget = 3 и корректную работу при budget = 1, 2, 5.

### Минимизация воспроизведения падающего сценария (Этап 3)
Для минимизации выбран многошаговый сценарий «T06: R03 удержание аварии fault и восстановление по reset» (исходно 4 шага: перевод в fault -> проверка удержания при reset=false -> сброс при reset=true -> проверка сохранения памяти гистерезиса).
- Кратчайшая последовательность для воспроизведения BUG-02 состоит из **2 шагов**:
  1. Шаг 1 (`age = 31, reset = false`): переводит контроллер из стартового состояния `NORMAL` (`fault = false`) в аварийное состояние `FAULT` (`fault = true`).
  2. Шаг 2 (`humidity = 20, temp = 20, age = 0, tank = 50, budget = 5, rain = false, reset = false`): подаёт валидный свежий снимок без команды сброса и демонстрирует расхождение (ожидается `fault = true, pump = false`, факт — `fault = false, pump = true`).
- Почему удаление любого из оставшихся шагов убирает воспроизведение:
  * Шаги 3 и 4 исходного сценария проверяли восстановление по `reset = true` и поведение гистерезиса после сброса — их удаление не влияет на проявление BUG-02, так как нарушение происходит уже на шаге 2.
  * Удаление **шага 1** делает воспроизведение невозможным: каждый независимый сценарий начинается с `fault = false` (R11), поэтому без подготовительного шага 1 условие `previous.fault` на шаге проверки не будет истинным, и дефект в логике удержания аварии (`hold`) не активируется.
  * Удаление **шага 2** убирает сам шаг наблюдения отказа (остаётся только штатный переход в аварию на шаге 1, который в `candidate.js` работает корректно).

Детерминизм и повторяемость | Два независимых запуска полного сценария с идентичным начальным состоянием (`false, false, false`) и идентичной последовательностью входов | Пошаговые выходы `(pump, vent, fault, used)` полностью совпадают на каждом шаге | Не выполняется при сравнении одиночных шагов, взятых из середины разных историй с разным внутренним состоянием памяти. |

Бюджет 2 -> 3 при двух запросах (немонотонность для насоса):
- **Исследование свойства:** при одинаковом начальном состоянии (`pump = false, vent = false, fault = false`) и одновременном запросе обоих устройств (`humidity = 20 < 35` и `temp = 31 >= 30`, без запретов полива):
  * При `budget = 2`: вентиляция требует 3 ед. и не помещается (`ventFits = false`, `vent = false`); остаток бюджета 2 ед. проверяется для насоса (`pumpFits = true`), поэтому **насос включается** (`pump = true, vent = false, used = 2`).
  * При `budget = 3`: первой рассматривается более приоритетная вентиляция (`order = ['vent', 'pump']`), бюджета 3 хватает ровно на неё (`ventFits = true`, `vent = true`, остаток `3 - 3 = 0`); на насос остаётся 0 ед. (`pumpFits = false`), поэтому **насос выключается** (`pump = false, vent = true, used = 3`).
- **Вывод:** увеличение бюджета с 2 до 3 переводит насос из состояния `ON` в `OFF`. Это **не является дефектом**, а представляет собой штатное следствие приоритетного распределения неделимого ресурса (R09), где вентиляция имеет более высокий приоритет безопасности, чем полив.

## 7. Взаимная проверка
Рецензент: Взаимная проверка выполнена по правилам контрольного аудита доказательств (проверка воспроизводимости оракулов и критический анализ ложноположительных выводов).
Проверенный оракул и ручной расчёт:
- Проверен независимый оракул для сценария конкуренции за ограниченный бюджет и удержания памяти гистерезиса при сбросе аварии (`T06`, шаг 3–4 и `T10`, шаг 2–3):
  * Вход: `humidity = 20, temp = 31, age = 0, tank = 50, budget = 3, rain = false, reset = false` при стартовом состоянии `pump = false, vent = false, fault = false`.
  * Ручной расчёт по спецификации: вход валиден (`R01`), свежий (`age = 0 <= 30`, `R02`), аварии нет (`R03`). Вентиляция запрашивается (`temp = 31 >= 30`, `R04`), насос запрашивается (`humidity = 20 < 35`, `R05`), запретов полива нет (`temp > 3`, `rain = false`, `tank >= 10`, `R06–R08`). При распределении бюджета (`R09`) первой рассматривается вентиляция стоимостью 3 ед.: остаток `3 >= 3` -> `vent = true`, остаток `0`. Далее рассматривается насос стоимостью 2 ед.: остаток `0 < 2` -> `pump = false`. Итоговый выход: `pump = false, vent = true, fault = false, used = 3`.
- Разбор двух ложноположительных выводов:
  1. **«Больше бюджет всегда улучшает работу насоса» (ложный вывод):** опровергнут аналитически и экспериментально на переходе `budget = 2 -> 3` при одновременном запросе обоих устройств (`T10`, шаги 2–3). Рост бюджета с 2 до 3 переводит насос из `ON` в `OFF`, так как появляющегося ресурса начинает хватать на более приоритетную вентиляцию (стоимость 3 ед.), которая забирает весь бюджет и вытесняет насос.
  2. **«Все 8/8 мутаций убиты, значит невалидный ввод полностью проверен» (ложный вывод):** опровергнут анализом набора мутаций `M1…M8` в `engine.js`. Мутации затрагивают только пороги `pumpStart`, `pumpStop`, `ventStart`, `fresh`, `hold`, `order`, `cold` и `lowTank`, и **ни одна из них** не изменяет функцию валидации `valid(x)` (`R01`). Убийство 8/8 мутаций подтверждает качество проверки граничных условий бизнес-логики, но абсолютно не доказывает полноту проверки типов данных, структурных ошибок и внешних границ диапазонов.

Предложенная непроверенная комбинация:
- Из таблицы решений 8 сочетаний блокировок полива (Раздел 3) ранее были оставлены непроверенными комбинации 5–8 (одновременное действие двух или трёх запретов). Для контрольного воспроизведения выбрана **комбинация 8** (одновременный холод, дождь и низкий уровень воды при сухой почве):
  * Вход: `{ "humidity": 20, "temp": 3, "age": 0, "tank": 9, "budget": 5, "rain": true, "reset": false }` при начальном состоянии `pump = false, vent = false, fault = false`.
  * Ожидаемый результат: `pump = false, vent = false, fault = false, used = 0` (все три запрета блокируют полив без фиксации аварии `fault`).
- Также сформулированы **критерии приёмки следующей версии (2.1)** и **требования к наблюдаемости реальной системы**:
  * *Критерии приёмки 2.1:* 100% прохождение регрессионного набора 2.0 (за исключением запланированной дельты в диапазоне `35 <= humidity < 40`), 100% прохождение расширенного `delta-tests.json` с граничными точками `39.9 / 40 / 40.1`, обновление мутации `M1` под порог `40` и убийство всех мутаций `8/8`.
  * *Наблюдаемость реальной системы:* метки времени (`timestamp`) каждого измерения и управляющего воздействия; энергонезависимый журнал событий и причин перехода в `FAULT` (`reason`); протокол подтверждения доставки команды до контроллера (ACK/NACK); обратная связь от датчиков фактического состояния исполнительных механизмов (ток обмотки насоса, датчик потока воды, тахометр вентилятора) для обнаружения расхождения между командой и реальным включением.

Результат воспроизведения:
- Проверочный прогон комбинации 8 на стенде с исправленной сборкой `candidate-fixed.js` полностью подтвердил ручной оракул (`pump = false, vent = false, fault = false, used = 0`, статус `PASS`). Чужие дефекты и регрессионные тесты воспроизводятся детерминированно по приложенным JSON-наборам.

## 8. Решение
Принять / принять с ограничениями / отклонить учебную сборку:
**ПРИНЯТЬ УЧЕБНУЮ СБОРКУ (`candidate-fixed.js`) С ОГРАНИЧЕНИЯМИ (строго в рамках учебной дискретной модели версии 2.0).**

Доказательства:
1. **Полная прослеживаемость требований:** спроектированы и выполнены 12 сценариев (36 шагов) в наборе `tests-final.json`, покрывающие все нормативные требования `R01–R11`, внешние и внутренние границы с шагом `0.1` и `1`, ошибки типов/структуры, переходы `NORMAL <-> FAULT` и многошаговую память гистерезиса.
2. **Выявление и устранение всех дефектов поставщика:** на этапе испытаний чёрного ящика обнаружены и задокументированы 3 дефекта (`BUG-01` на границе `humidity = 35`, `BUG-02` в удержании `fault`, `BUG-03` в приоритете бюджета `order`). После внесения точечных исправлений в `candidate-fixed.js` повторный прогон (`protocol-final.txt`) показал **100% прохождение всех 12 сценариев (36/36 шагов `PASS`)** без регрессий.
3. **Высокая сила тестового набора:** достигнуто **24/24 (100%)** покрытия учебных исходов решений и обнаружено **8/8 (100%)** мутаций контрольной модели.
4. **Готовность к развитию:** подготовлен анализ влияния перехода на версию 2.1 (`change-impact.txt`) и набор различающих тестов (`delta-tests.json`).

Остаточные риски:
1. **Отсутствие моделирования реальной физики и оборудования:** модель не учитывает фактический расход воды из бака (`tank`) при работе насоса, реальное потребление электроэнергии, инерционность прогрева/охлаждения теплицы и износ реле при частых переключениях.
2. **Отсутствие аппаратной безопасности и защиты от зависаний:** сброс аварии по флагу `reset = true` выполняется программно на одном логическом шаге без аппаратного подтверждения исправности датчиков и без таймера удержания (watchdog).
3. **Неполнота комбинаторного покрытия:** при достижении 24/24 учебных исходов в наборе не проверялись все комбинации одновременных невалидных полей и длительные многочасовые последовательности переключений.

Что потребовалось бы для реальной системы:
- Реализация аппаратных блокировок (защита насоса от сухого хода по поплавковому датчику помимо программного `tank < 10`), контроль фактического исполнения команд через обратную связь с реле/датчиков потока, ведение криптографически защищённого журнала аварий с привязкой к реальному времени и внедрение гистерезиса по времени (минимальное время работы и паузы насоса) для защиты двигателя.

Чего мы не успели / не проверили (не скрывать):
- Не проведено нагрузочное/длительное тестирование на длинных цепочках (50+ шагов подряд в одном сценарии) с многократным чередованием аварий и сбросов.
- Не проверены одновременные комбинации двух и более невалидных полей в одном JSON-объекте (`R01`), а также поведение при экстремальных значениях JS-чисел (`NaN`, `Infinity`, `-Infinity`, которые не сериализуются в стандартный JSON, но могут поступить при прямом программном вызове `step()`).
- Не реализована и не протестирована программная ветка контроллера версии 2.1 (выполнен только анализ влияния и подготовка `delta-tests.json`, так как изменение эталонной 2.0 запрещено условиями приёмки).
