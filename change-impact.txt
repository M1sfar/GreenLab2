# Анализ влияния изменений при переходе на спецификацию GreenLab 2.1

## 1. Суть предлагаемого изменения
Заказчик предлагает изменить правило запуска полива для особо ценной культуры:
- **Версия 2.0 (текущая):** полив запрашивается при `humidity < 35`, выключается при `humidity >= 45`, зона гистерезиса `35 <= humidity < 45`.
- **Версия 2.1 (предлагаемая):** полив запрашивается при `humidity < 40`, выключается при `humidity >= 45`, зона гистерезиса `40 <= humidity < 45`. Остальные правила (`R01–R04`, `R06–R11`) остаются без изменений.

## 2. Затронутые требования, состояния и компоненты
- **Требование R05 (запрос полива):** изменяется нижний порог включения насоса с `35` на `40`, а интервал сохранения предыдущего фактического состояния насоса (`previous.pump`) сужается в два раза — с `[35; 45)` (ширина 10%) до `[40; 45)` (ширина 5%).
- **Связанные правила (косвенное влияние):**
  * **R06, R07, R08 (защитные запреты полива):** чаще активируются в диапазоне влажности `[35; 40)`, так как теперь при этих значениях формируется запрос на включение насоса (`pump = true`), который при наличии холода (`temp <= 3`), дождя (`rain = true`) или малого уровня воды (`tank < 10`) будет принудительно заблокирован.
  * **R09, R10 (распределение бюджета и расход `used`):** в интервале влажности `[35; 40)` при старте с выключенного насоса расход бюджета возрастает с `0` до `2` единиц (при достаточном бюджете и отсутствии запретов), а при одновременном запросе вентиляции (`temp >= 30`) порог полного покрытия обоих устройств смещается с `3` до `5` единиц в этом диапазоне влажности.
- **Программные модули:** потребуется изменение функции `pumpStart` в `policies.reference` (`assets/engine.js`) и в сборке поставщика (`assets/candidate.js`), а также корректировка мутации `M1` (в 2.0 она проверяла `h <= 35`, для 2.1 потребуется мутация на границе `h <= 40`).

## 3. Затронутые тесты и оракулы из набора 2.0 (`tests-final.json`)
При прогоне набора 2.0 против реализации 2.1 изменятся оракулы в следующих сценариях:
1. **`T05` (шаги 1 и 2 — точки `humidity = 35.1` и `humidity = 35`):** в 2.0 ожидалось `pump = false, used = 0`; в 2.1 оба значения строго меньше `40`, поэтому ожидается `pump = true, used = 2`. Кроме того, старые граничные точки `34.9 / 35 / 35.1` перестают проверять порог старта и должны быть заменены на `39.9 / 40 / 40.1`.
2. **`T09` (шаг 2 — История Б, вход `humidity = 40, temp = 28` после `OFF`):** сохраняет ожидание `pump = false` (так как `40` остаётся левой границей гистерезиса `[40; 45)`), но для демонстрации сохранения состояния в зоне гистерезиса 2.1 потребуются точки внутри `[40; 45)` (например, `humidity = 42`), а значения `35..39.9` больше не являются зоной гистерезиса.

## 4. Риск обратной несовместимости и недостаточность правки одного порога
- **Риск обратной несовместимости (Высокий):** контроллер версии 2.1 нарушает обратную совместимость с прошивкой 2.0 на всём полуинтервале влажности `35 <= humidity < 40` при условии `previous.pump = false`. Существующие сценарии эксплуатации и автоматические регрессионные тесты версии 2.0 начнут падать.
- **Почему недостаточно изменить только одну константу (`35 -> 40`) в коде:**
  1. Устареют граничные тесты и оракулы: проверка `34.9 / 35 / 35.1` перестанет ловить ошибку нестрогого неравенства (`<= 40` вместо `< 40`), а мутация `M1` (`h <= 35`) в стенде станет эквивалентной или неадекватной новой границе.
  2. Сужение зоны гистерезиса с 10% до 5% увеличивает частоту переключений насоса при колебаниях влажности и повышает потребление бюджета в диапазоне `[35; 40)`, что требует регрессионной проверки сценариев конкуренции за бюджет (`R09`) и сохранения памяти (`R10`) на новых границах.
